## 1. Build Installer now downloads a real Windows `.exe`

**Before:** The "Windows (.exe / .bat)" option built a `.bat` text file in the browser, and that file had several problems:
- It sent a hard-coded IP address and a random machine ID.
- The Linux `.sh` option sent an empty request.
- The Python option only printed a line.
- **COPY URL** pointed to `/api/download-agent`, which did not exist.
- **SEND LINK** showed "sent" without sending anything.

**Now:**
- **DOWNLOAD** with **Windows (.exe)** returns a genuine Windows program, for example `ITPortalAgent_Meditab.exe`. It is about 11 KB and is a real `MZ` executable.
- The backend compiles it on request from [`backend/agent/ITPortalAgent.cs`](../backend/agent/ITPortalAgent.cs), using the C# compiler that ships with Windows (`C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`). You don't need to install anything.
- The Company, Site, Department, Device Type, Name and Portal URL you enter in the form are compiled into that `.exe`.
- Each unique combination is compiled once and then served from a cache: the first build takes about 0.7 s, repeats about 0.07 s. The cache is `backend/agent/build/` and keeps the 20 newest builds.
- When the `.exe` runs on a PC, it:
  1. Shows the portal address and the details it will send: hostname, IP, user, Windows version and labels.
  2. Asks **"Register this computer with the portal? [Y/n]"**.
  3. Registers the PC once, then exits. It installs nothing and doesn't keep running in the background.
- For scripted rollout, run `ITPortalAgent_<Company>.exe /y` (or `--yes`) to skip the prompts.
- The machine ID comes from the Windows MachineGuid, so running the installer again **updates** the same entry instead of creating duplicates. The Python agent uses the same ID.
- If you re-run an installer that was built with blank labels, the labels already stored for that machine are kept.
- **Linux (.sh)** and **Python (.py)** are now generated by the backend too, and both register correctly.
- **Portal Server URL** field (new):
  - Pre-filled with this server's LAN address (from `/api/server-info`).
  - Shows a warning if you enter `127.0.0.1` or `localhost`, because remote PCs can't reach those.
- **Custom Name** field: appears when Name is set to "Custom Name".
- **COPY URL** copies a working download link. If the clipboard is blocked, it shows the link to copy.
- **SEND LINK** opens a pre-filled email draft in your mail app.
- The leftover "test:" field was removed.

**Things to know**
- The `.exe` is **not code-signed**, so Windows SmartScreen or the browser may warn "unknown publisher" the first time. Choose *More info → Run anyway*. Code signing is listed in [FUTURE_ENHANCEMENTS.md](FUTURE_ENHANCEMENTS.md).
- Building `.exe` files needs the backend to run on **Windows**. On other operating systems the endpoint returns a clear 503 message; use the Python agent there.
- For other PCs to register, the backend must be reachable on the LAN: start it with `--host 0.0.0.0` (see *How to run*) and allow port 8000 through the Windows firewall.

## 2. Assets page shows data again

There were several separate causes. All are fixed:

1. **Wrong database file (main cause).**
   - `main.py` opened `tickets.db` by *relative* path, so the file it used depended on the folder uvicorn was started from.
   - `./tickets.db` in the project root has **0 assets**. `backend/tickets.db` has your **5 assets**.
   - **Fix:** the database is now always `backend/tickets.db`, wherever you start the server.
   - On first start, the 2 tickets that existed only in the root `tickets.db` (INC-3158 and INC-8471) are copied in once. The old file is never changed or deleted.
2. **Stat cards always showed 0.** The card ids in `assets.html` didn't match the ids the script updated. The ids are fixed, and the "Undeployed" card is relabeled **Deployed** (it holds the deployed count).
3. **Duplicate code.**
   - `app.js` contained two copies of the asset functions and two form-submit handlers.
   - As a result, every save sent **two** requests, and every edit showed a false "Failed to save asset" message.
   - Only one copy is left now: an edit sends exactly one `PUT`.
4. **Silent failures.** The table now shows a *Loading…*, *No assets yet* or *Can't reach the backend at 127.0.0.1:8000* row instead of staying blank.
5. **Smaller fixes:**
   - Header and Logout button added.
   - Correct menu item highlighted.
   - Modal title shows "Edit Asset …" when editing.
   - The Asset Tag field no longer stays locked after Cancel.
   - Check In now asks for confirmation instead of asking for a name.
   - Status badges are styled.
   - Search keeps working after the table refreshes.

## 3. Click anywhere on a ticket row → quick-view popup

- Clicking any cell of a ticket row, or pressing **Enter** on a focused row, opens the **Ticket Details popup** (quick view).
- The **View ↗** button no longer opens the popup: it opens the full ticket in a new tab (see 4).
- Press **Esc** to close the popup.
- A 💬 chip on the row shows how many notes the ticket has.
- The popup header has an **"Open full ticket in a new tab ↗"** link.

## 4. New: Ticket Details page (`ticket-details.html`), opened in a new tab by "View"

A full page for one ticket, at `ticket-details.html?id=INC-1234`. You can bookmark it, share it, and keep several tickets open at once.

- **Header:** "← Back to Tickets", the ticket ID and subject, status and priority pills, and Logout.
- **Left column:**
  - **Description**, with line breaks kept.
  - **Notes & Activity**, the full notes panel (see 5).
- **Right column:**
  - **Ticket Details:** edit **Status, Priority, Category and Assigned To**, then **Save Changes**. Assigned To suggests existing assignees and you.
  - **Requester:** name and a clickable email address.
  - **Summary:** created date, assignee, **total time spent**, and note counts by type.
- Shows friendly screens for *Ticket not found* and for *can't reach the backend*.
- Responsive: two columns on wide screens, one column below 1200 px, with no sideways scrolling on phones.
- **Auto-refresh across tabs:** when you save a ticket or change a note on this page, the Tickets and Dashboard tabs that are already open refresh by themselves. It also works the other way: changes made in the Tickets tab show up on an open details page, and anything you're still typing is kept.
- **Save Changes sends only the fields you changed**, so a tab that has been open a long time can't undo someone else's update.

## 5. Notes: what was fixed

The same notes panel is used in the popup and on the details page.

| Problem before | Now |
|----------------|-----|
| Notes were kept only in the browser and disappeared on refresh | Saved in the database (new `ticket_notes` table) with author and time |
| Discussion / Internal / Resolution tabs did nothing, and both counters showed the same number | Choose the note type when adding. The tabs filter the list, and each tab shows its own count |
| No way to edit or delete | **Edit** changes the text, type or time, and the note shows "edited". **Delete** asks for confirmation first |
| No time tracking | **Time spent** (hours + minutes) per note, shown as ⏱ on the note, with the ticket's total in the Summary |
| Note text was inserted as HTML, so text could break the page | Text is shown safely as plain text, with line breaks kept |

**Extras:**
- **Ctrl+Enter** adds a note.
- An empty note shows an inline message.
- Internal notes are highlighted in amber and Resolution notes in green.

## How to run

**1. Install the backend packages** (one time):

```bash
pip install -r backend/requirements.txt
```

**2. Start the API.** You can start it from the project root or from `backend/`; both now use `backend/tickets.db`:

```bash
python -m uvicorn backend.main:app --host 0.0.0.0 --port 8000
```

- Use `--host 127.0.0.1` if only this PC needs access.
- `0.0.0.0` lets other PCs on the LAN register with the installers.
- The API has **no authentication** yet (see BUGS_FOUND O-01/O-02), so only expose it on a trusted network.

**3. Serve the frontend** with any static server, for example:

```bash
python -m http.server 5500
```

Then open `http://127.0.0.1:5500/index.html`. VS Code Live Server works too.

**Configuration**
- The frontend calls the API at `API_BASE` at the top of [`js/app.js`](../js/app.js) (default `http://127.0.0.1:8000`).
- `ITPORTAL_DB=<path>` (environment variable) makes the backend use a different database file, which is handy for testing on a copy.

## API changes

| Method & path | What it does |
|---|---|
| `GET /api/tickets` | Newest first. Each ticket now includes `notes_count` |
| `GET /api/tickets/{id}` | **New.** One ticket plus `notes_count` and `total_time_minutes`; 404 if missing |
| `POST /api/tickets` | `id` and `createdAt` are now optional. The server generates `INC-####` and returns `{"id": ...}` |
| `PUT /api/tickets/{id}` | Accepts any of `status`, `priority`, `category`, `assigned` and updates only the fields sent. The old `{status}` body still works. 404 / 422 / 400 on errors |
| `GET /api/tickets/{id}/notes` | **New.** Notes, newest first |
| `POST /api/tickets/{id}/notes` | **New.** Body `{note_type, author, text, time_spent_minutes}`. `note_type` is `discussion` \| `internal` \| `resolution` |
| `PUT /api/tickets/{id}/notes/{note_id}` | **New.** Partial update; sets `updated_at` |
| `DELETE /api/tickets/{id}/notes/{note_id}` | **New** |
| `PUT` / `DELETE /api/assets/{tag}`, `/api/remote-machines/{id}` | Now return 404 when nothing matched |
| `POST /api/remote-machines/register` | **New.** Used by the installers. Creates (201) or refreshes (200) a machine, including `company`, `site`, `department`, `device_type` and `last_seen` |
| `GET /api/server-info` | **New.** `{lan_ip, port, suggested_portal_url, windows_installer_available}` |
| `GET /api/download-agent?type=windows\|linux\|python&portal_url=&company=&site=&department=&device_type=&custom_name=` | **New.** Downloads the installer |
| `GET /api/remote-machines` | When no real machine exists yet, the sample machines now carry `"demo": true` |

## Database changes

All changes are made automatically on startup and are safe to run again:
- **New table `ticket_notes`:** `id`, `ticket_id` (linked to `tickets.id`; notes are deleted with their ticket), `note_type`, `author`, `text`, `time_spent_minutes`, `created_at`, `updated_at`.
- **`remote_machines`** gets the new columns `company`, `site`, `department`, `device_type` and `last_seen`.
- **New table `app_meta`:** remembers that the one-time import from the old root `tickets.db` has run.

## How this was tested

- **API:** every new and changed endpoint was called against a *copy* of the database, checking success cases, 404, 422 and 400 responses, and the legacy import.
- **Installers:**
  - `.exe` downloaded, checked (`MZ` header, file name), and run with `--yes`: it registered, and running it again updated the same entry.
  - A malicious label value stayed plain text inside the `.exe`.
  - The `.sh` and `.py` agents downloaded and registered.
- **Browser**, at 1024 px, 1440 px and 375 px wide:
  - login
  - tickets: row click, Enter key, View button, search
  - popup notes
  - details page: add, edit and delete notes, time totals, save, not-found state, cross-tab refresh
  - assets: data, stats, a single `PUT` on edit, search
  - remote: counts, filters, search, installer modal, `.exe` download
  - dashboard
  - no console errors except the intentional 404 test
- **Independent review:** after the work was done, a review of all new code confirmed 16 more issues (race conditions, cross-tab staleness, CSS breakpoints…). All 16 were fixed and re-tested; see the last section of [BUGS_FOUND.md](BUGS_FOUND.md).
- Your real `backend/tickets.db` and the root `tickets.db` were **not modified** during testing (checksums identical before and after). The new tables are added the first time you start the new backend.
